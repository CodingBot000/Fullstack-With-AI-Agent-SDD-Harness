# SDD 작업 흐름

## 1. 조사와 범위
요청이 제품 기능 개발인지, 기존 결함 수정인지, 하네스 개선인지 구분한다. 소스/빌드/테스트/현재 동작을 읽고 요구사항과 실제 구현 사이의 차이를 기록한다. 공식 문서는 현재 프로젝트 버전에 맞춰 확인하며 조회 사실과 설계 제안을 구별한다.

## 2. 요구사항과 설계
사용자 문제, 관찰 가능한 성공, 실패/복구, 제외 범위, 데이터/권한, 응답 계약을 적는다. 구현 도구는 요구사항과 분리한 design에 기록한다. 알 수 없는 목표치를 수치로 만들어 넣지 않는다. 결정이 필요한 부분은 미확인으로 남기고 위험에 맞게 승인받는다.

작은 국소 수정은 spec/design/tasks를 짧게 작성할 수 있다. 인증·데이터 손실·외부 쓰기·여러 계층·AI 정책 변경은 영향 분석과 전체 문서를 작성한다. 문서 길이가 아니라 요구사항·테스트·변경 연결을 기준으로 한다.

```bash
python3 scripts/harness.py new-change <change-slug> --areas frontend backend ai --risk medium
```

위 areas는 명세 범위 예시일 뿐 실제 제품 구성을 강제하지 않는다. RAG/Agent/streaming이 필요할 때만 추가한다. 생성 직후 문서는 미완성이며 승인 상태가 아니다.

## 3. 작업과 실행
각 작업은 관련 요구사항 ID, 변경 경로, 선행 작업, 검증 명령, 완료 증거를 연결한다. 계약을 먼저 합의하고 작은 수직 기능 단위로 구현한다. 병렬화는 독립 소유 범위에만 사용한다. 공유 스키마·API·마이그레이션 변경은 통합 책임자가 조정한다.

## 4. 검증과 개선
변경 전 baseline/실패 재현 → 구현 → 실제 명령 실행 → AI 평가(해당 시) → 원인 분석 → 재검증을 반복한다. 같은 평가 데이터로만 프롬프트를 최적화하지 말고 holdout을 분리한다. 품질 개선은 비용/지연/안전성 악화와 함께 판단한다.

## 5. 리뷰·완료
독립 검토자는 스펙 위반·보안·회귀·의미 없는 테스트·eval 누수를 확인한다. 문서의 승인 필드는 실제 사용자/리뷰어 승인 링크를 기록하기 위한 것이며 에이전트의 자가 승인 수단이 아니다. `verification.md`와 `change.json`에 증거를 연결한다. 미실행 항목은 완료로 처리하지 않는다.

## 이 킷이 자동화하는 범위
CLI는 문서 틀, 필수 필드, 요구사항 ID와 검증 참조, 실제 명령/평가 성공 여부를 검사한다. 요구사항이 충분한지, 테스트가 요구사항을 의미 있게 검증하는지, 승인 링크가 진짜인지까지 자동 판정하지 않는다. 그 부분은 PR 리뷰와 저장소 권한 정책의 책임이다.
